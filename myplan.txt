Functional Architecture Prompt

Build a production-ready email verification web application using Cloudflare-only infrastructure wherever possible. The current scope is functional completeness, not visual/UI completeness. Implement the complete backend, authentication, database, verification engine, retention, API, security, and deployment architecture. The landing page only needs a simple email search field and Google Login button for now.

1. Technology decisions

Use exactly this stack unless technically necessary to change:

TypeScript
Cloudflare Workers for the backend/API
Cloudflare D1 for persistent application data
Cloudflare KV for caching
Cloudflare Cron Triggers for scheduled cleanup
React + Vite + TypeScript for the frontend
Cloudflare Workers Static Assets / Pages-compatible deployment for the frontend
Google OAuth 2.0 / OpenID Connect for Google Login
REST JSON API between frontend and Worker
No Python backend
No VPS
No Redis
No PostgreSQL
No paid third-party authentication service
No paid email-verification API in the initial version

The application must be deployable using Cloudflare's free-tier resources within their applicable limits.

CREATE TABLE users (

    google_sub TEXT UNIQUE,

    created_at TEXT NOT NULL,

CREATE TABLE sessions (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,

7. Five-day data retention

User accounts are permanent unless the user deletes their account.

Verification data is temporary.

Every verification must have:

created_at


The application must retain verification records for approximately five days and automatically delete records older than five days.

Cloudflare Cron:

Once every 24 hours
        ↓
cleanup()
        ↓
Delete verification records older than 5 days
        ↓
Delete expired sessions
        ↓
Delete expired bulk jobs


Use a parameterized SQL query.

Example:

DELETE FROM verifications
WHERE created_at < datetime('now', '-5 days');


Also clean expired sessions:

DELETE FROM sessions
WHERE expires_at < datetime('now');


The cleanup must be safe to run repeatedly.

Do not delete the user's Google account record during normal cleanup.

Reject malformed input

For example, do not automatically remove dots or plus-tags unless explicitly implementing provider-specific rules.

Store:

normalized email

9. Email syntax verification

Implement standards-aware validation without attempting to support every obscure RFC edge case.

Return:

PASS
FAIL


Examples:

[email protected] → PASS
abc@@example.com → FAIL
abc → FAIL
@example.com → FAIL


Do not use an enormous fragile regex.

10. Domain verification

Extract the domain.

Check whether the domain can resolve.

Return:

DOMAIN_EXISTS
DOMAIN_NOT_FOUND
UNKNOWN


Do not equate DNS existence with mailbox existence.

11. MX verification

Check MX records.

Return:

MX_FOUND
NO_MX
UNKNOWN


If the domain has no usable mail-routing mechanism, the final risk score should increase substantially.

Cache domain-level DNS/MX results in KV with a sensible TTL.

12. SPF

Check the domain's TXT records for SPF.

Return:

SPF_PRESENT
SPF_MISSING
SPF_INVALID
UNKNOWN


Do not treat missing SPF alone as proof that an email is fake.

13. DMARC

Check:

_dmarc.example.com


Return:

DMARC_PRESENT
DMARC_MISSING
DMARC_INVALID
UNKNOWN


Again, use it as a reputation/security signal rather than proof of mailbox existence.

14. Disposable email detection

Use KV for caching.

Example:

Return:

DISPOSABLE
NOT_DISPOSABLE
UNKNOWN


Do not claim that a domain is disposable merely because it is unfamiliar.

16. Catch-all detection

If a safe and technically reliable implementation is available, expose:

CATCH_ALL
NOT_CATCH_ALL
UNKNOWN


Do not falsely claim mailbox existence.

Do not repeatedly probe arbitrary mail servers aggressively.

If catch-all cannot be reliably determined, return UNKNOWN.

17. SMTP verification

Do not make SMTP mailbox probing a mandatory dependency in version 1.

The system should support a future provider/component:

SMTP verification
      ↓
optional signal


The core application must function without it.

Do not classify an email as definitely real solely because an SMTP server accepts a recipient.

18. Final scoring engine

Create a deterministic scoring system.

Possible signals:

Syntax failure          → very high risk
Domain unavailable      → very high risk
No MX                   → very high risk
Disposable              → very high risk
Role account            → moderate risk
Suspicious DNS          → moderate risk
Missing SPF             → small risk
Missing DMARC           → small risk
Catch-all               → small/moderate risk
Valid syntax            → reduces risk
Valid domain            → reduces risk
Valid MX                → reduces risk


The scoring system must be configurable in one place.

Do not hard-code scoring logic throughout the application.

Final verdicts:

LIKELY_DELIVERABLE
RISKY
LIKELY_INVALID
DISPOSABLE
ROLE_ACCOUNT
NO_MX
INVALID_SYNTAX
UNKNOWN


A score must never be presented as absolute proof.

37. Production principles

The finished project must:

Have no fake verification results.
Never claim a mailbox is 100% real when the evidence cannot establish that.
Fail safely when DNS services are unavailable.
Avoid excessive SMTP probing.
Keep user verification records for only five days.
Automatically delete expired records.
Keep user accounts separate from temporary verification data.
Never expose credentials.
Never trust client-side authorization.
Keep all verification decisions server-side.
Be structured so future verification providers can be added without rewriting the core application.
